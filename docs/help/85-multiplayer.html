Playing together

Open Netplay Playground from the Studio's Examples list. It makes a copy in a folder you choose, just like Breakout. This example has two games for two to four players on the same local Wi-Fi network. Each person uses their own handheld, running the same copy of the game and a runtime with multiplayer support. Internet matchmaking is not supported.

Start with practice

Run the game and choose Practice here. Left and right choose a game; A starts it. The board game passes one handheld between two people. The platformer is a solo run to collect five stars. Practice does not open a network connection, so you can learn the controls before connecting another device.

Connect two handhelds

  1. Send the same game to both handhelds and enable Wi-Fi in each handheld's system settings. Connect them to the same network. Avoid a guest network that prevents devices from communicating.
  2. In the game's menu, select Name and use left and right to pick different names. The game remembers a name after you host or join.
  3. On one handheld choose Host on Wi-Fi. On the others choose Join on Wi-Fi, select that host, and press A. Player numbers and names appear in the lobby; the host is always Player 1.
  4. The host uses left and right to choose a game, then A starts everyone together. At least two players must be in the lobby. You cannot join a round already in progress.

If no host appears, check Wi-Fi, that both copies have the same title and console, and that your network allows local UDP traffic. On one computer, testing uses GS_NET_DISCOVERY=127.0.0.1 for local discovery; that switch is not for handheld play.

Three in a row: turn-based play

Players take turns on a five-by-five board. The D-pad moves the shared cursor; A places your piece. Make a line of three horizontally, vertically, or diagonally to win. Only the player whose turn it is can move or place a piece. Each player has a different colour and shape. An occupied square does not use up your turn, and a full board without a line is a draw.

Star sprint: live platform play

Everyone moves at once. Left and right run, A jumps, and Down drops through a raised platform. The first player to collect five stars wins. Players pass through each other; if two reach the same star in one step, the lower player number gets it. The course has no pits, so a missed jump is a chance to try again, not a lost life.

At the end of either game, Player 1 presses A for another round or X for the other game, without making a new Wi-Fi lobby. In practice, the same buttons work on the one handheld. B leaves a game; during Wi-Fi play that ends the session for everyone.

Try interruptions too

Open the system menu on one handheld while playing. The other should stop and show who it is waiting for, then continue when the first handheld returns. A missing input pauses simulation instead of guessing where a player went. After a long wait, the waiting screen offers B to leave. Save states, Resume, and rewind are unavailable while a network connection is open. Saving a code change ends the session, so make changes between sessions and update every device.

This is experimental networking. Netplay Playground has been reported working between a TrimUI Brick running NextUI and an Anbernic RG35XX Pro running Knulli. That confirms this pairing, not every firmware, four-handheld play, long sessions or interruption recovery. The automatic tests also cover two and four processes, mode changes and rematches.

Build your own multiplayer game

Keep the normal editable project structure: actors in entities/, rules in scene code, and authored terrain, starting positions and HUD elements in scene layouts. Networking sends numbered button presses, not entity positions. Every device loads the same resources and runs the same rules.

  1. Set players = 2, 3 or 4 in game.lua. This is the maximum, not the current player count. Leaving it out means a single-player game. Keep the title, console and player count in Game info consistent.
  2. Make a local menu with gs.net.host(name), gs.net.find() and gs.net.join(id, name). Discovery returns sessions with id, name, players and max. Call find() from the discovery screen's update, not just once. Names are 1–32 bytes without control characters.
  3. Show gs.net.peers() in the lobby. Watch gs.net.state and gs.net.error while joining. Opening or joining can fail: show the reason rather than silently returning to the menu. Copy the example menu's error handling if you need a starting point.
  4. Once at least two players are present, the host calls gs.net.start("scenes.play"). The engine shares the host's save and seed, resets the world and enters the same scene on every device.
  5. In an actor, keep a player field and read gs.input.dir(self.player), gs.input.pressed("a", self.player), held and released. Every device updates every actor, not just the actor owned by that device. With no player argument, input still means Player 1, not “this handheld.”
  6. Handle on_net_end(reason) in the scene to show the reason and return to the menu. gs.net.leave() ends the session for everyone; there is no replacement player or late joining.

Initialise all shared round state in enter(), including any shared lib/ tables. Do not carry menu counters, cached random values or local name choices into the simulation. The layout is built before enter(), so a layout actor's own initialisation must be deterministic too. Use the session's seeded math.random, or give gs.rng(seed) the same explicit seed on every device. Do not use the wall clock, device-dependent table iteration or drawing to change gameplay state.

gs.net.me is only for a private view: a “You” label, a local camera or a private hand of cards. A private camera must not affect gameplay, collision tests, spawn decisions or shared state. The host's save snapshot is currently limited to 64 KB; guests use it for the session without overwriting their own progress.

With an agent

The MCP server exposes this page as help("multiplayer") or help("netplay"), and the full networking reference as api("gs.net"). Use overview to see a game's layouts and declared player count.

netplay starts two to four independent runtime processes, connects them over local UDP and starts a scene. For example: netplay({ game: "netplay-playground", scene: "sprint", players: 2, seconds: 3 }). An optional bot_lua defines bot_step() for each device's own buttons; it runs after the session starts. Use gs.input.sim_hold("right", true) to hold a local button, and set it to false to release it. Use gs.net.me in the test bot to give each device different inputs, never to skip gameplay updates.

The tool reports start/completion failures, compares common scalar-state checkpoints and returns a screenshot from each peer. Matching checkpoints do not prove full determinism: nested tables, timers and random-generator internals are not included. This tool bypasses your lobby, uses temporary saves, and does not send anything to a handheld. Also test the actual menus and both devices. A single run or check does not test a network session.

If something goes wrong

What happensWhat to check
No host appearsBoth devices need Wi-Fi, the same local network, matching game files and runtime builds, and the same title and console. Avoid guest/client isolation, VPN routing and firewalls blocking local UDP port 45843. Discovery is not a content-version check.
The menu ignores buttons on KnulliSend the game again with an up-to-date Studio deployment. The launcher must use Knulli's controller mapping, including on a fresh install that has never run another emulator.
The game says it is waitingReturn from the other handheld's system menu and check its Wi-Fi and battery. Do not use fast-forward or rewind. After 30 seconds, B can end the stalled session.
The game says players are out of stepUpdate every device to the same build and restart the session. Check initial state, seeded random choices, drawing side effects and any use of gs.net.me in gameplay.

There is no internet matchmaking, authentication, adaptive input delay or automatic full-state recovery. Input delay is fixed at two simulation steps (about 33 ms at 60 steps per second), plus any wait for missing packets. Use a trusted local network. Two hosts on one computer need different GS_NET_PORT values.

Read the example's code

scenes/menu.lua is the local lobby. scenes/board.lua holds the board as a string, the active turn and the shared cursor. scenes/sprint.lua starts every runner and chooses the next star; entities/runner.lua reads that runner's numbered input. The platforms and star locations are in lib/course.lua, and lib/playground.lua shares the drawing and end-of-session behaviour.

The important rule: every device updates every player. Use gs.input.pressed("a", player) and gs.input.dir(player), not just the local player's buttons. gs.net.me is for drawing the “You: P2” label, never for deciding which runner to update. Initialise gameplay in enter(), so time spent in different local menus does not affect the round. The API reference documents all the gs.net calls.
